MANCHESTER STOCK EXCHANGE (MSEG) SYSTEM
REQUIREMENTS IMPLEMENTATION ANALYSIS

================================================================================
1. PROGRAMME OVERVIEW AND LOGIC
================================================================================

The Manchester Stock Exchange system is a desktop application built using Python and Tkinter for the graphical interface. The application manages stock listing applications from companies and provides stock managers with tools to review applications, manage active listings, and perform market analysis.

The system follows a straightforward database-driven architecture. At the core is an SQLite database that stores all persistent data including user accounts, company applications, stock listings, and historical price data. The frontend uses Tkinter to create an intuitive interface where users can interact with the system through forms, buttons, and data tables.

When the application starts, it initialises the database connection and creates all necessary tables if they don't already exist. This ensures the system can recover gracefully even if the database file is deleted or corrupted. The application then displays a login page where users can authenticate as either a company or a stock manager.

The program logic is organised into several key modules. The database module handles all SQL operations and data persistence. The validation module contains functions that check user inputs against business rules before allowing data to be saved. The UI components are separated into different page classes, each representing a distinct screen in the application. This modular approach makes the codebase easier to maintain and test.

For stock price generation, the system uses a random walk model that creates realistic historical prices for newly approved stocks. This generates 366 days of price history with daily variations of plus or minus 1.5 percent, giving each stock a believable performance history that can be analysed.


================================================================================
2. FUNCTIONAL REQUIREMENTS IMPLEMENTATION
================================================================================

FR1: View Queue of Pending Applications
----------------------------------------

The manager portal displays all pending applications in a clean table format. When a stock manager logs in and navigates to the portal, the system queries the database for all applications with a status of 'pending' and displays them in a scrollable list. Each application shows the company name, proposed ticker, proposed shares, proposed valuation, and the date it was submitted.

The implementation uses a simple SQL query to fetch pending applications and then populates a Tkinter Treeview widget with the results. The manager can click on any application to view its full details including attached documents. This gives managers a complete overview of what needs reviewing without having to search through multiple screens.


FR2: Approve Valid Application
-------------------------------

When a manager approves an application, several things happen behind the scenes. First, the application's status in the database is updated to 'approved'. Then, a new stock record is created using the proposed ticker, shares, and valuation from the application. The sector that the company selected is also carried over to the stock listing.

The most important part of approval is the price history generation. The system calculates an initial stock price by dividing the proposed valuation by the proposed shares. Then it generates 366 days of historical prices using the random walk algorithm. This creates realistic daily price fluctuations that stay within a reasonable range. Once the price history is generated, the stock immediately appears in the stock market listing where all users can view it.


FR3: Reject Application with Reasons
-------------------------------------

The rejection process requires managers to provide a reason for their decision. When a manager clicks the reject button, a text input dialog appears prompting them to enter rejection notes. The system validates that this field is not empty before allowing the rejection to proceed.

Once a valid reason is provided, the application status is updated to 'rejected' and the rejection notes are stored in the database. The company can then log in to their account and view these notes on their applications page. This transparency helps companies understand why their application was unsuccessful and what they might need to improve for a future submission.


FR4: Integrity Check (Missing Fields, Duplicates, Unrealistic Valuations)
--------------------------------------------------------------------------

The system performs multiple validation checks before an application can be submitted. The ticker validation ensures the proposed ticker is between 3 and 4 capital letters with no numbers or special characters. It also checks the database to confirm that no existing stock already uses that ticker symbol.

Valuation checks ensure that proposed valuations fall within the acceptable range of 100 million to 500 billion pounds. Any valuation outside these bounds is rejected with a clear error message explaining the minimum or maximum requirement.

All required fields must be filled in before submission. The validation function checks that proposed ticker, proposed shares, proposed valuation, and sector are all present. It also verifies that at least one document has been attached to the application. If any of these checks fail, the submission is blocked and the user receives a specific error message identifying what needs to be corrected.


FR5: Regulatory Compliance Review
----------------------------------

Companies House verification is handled through an API integration with a fallback to an offline dataset. When a company registers, the system first attempts to verify their company name and registration number against the Companies House API. This ensures that only legitimate registered companies can apply for stock listings.

If the API is unavailable due to network issues or missing credentials, the system automatically falls back to a local CSV file containing company data. This fallback mechanism ensures the system remains usable even without internet connectivity.

The incorporation date validation checks that companies have been incorporated for at least 3 years. This is done by comparing the provided incorporation date against today's date and calculating the difference. Companies incorporated less than 3 years ago are rejected during registration with a clear message explaining the minimum age requirement.

Registration numbers must be unique across the system. Before allowing a new company to register, the database is checked to ensure their registration number has not already been used by another account.


FR6: Remove Stock Listing
--------------------------

Stock managers can remove stocks from the market through the stock listing page. Stocks are selected using checkboxes next to each listing in the table. When the manager clicks the delete button, a confirmation dialog appears to prevent accidental deletions.

Upon confirmation, the system deletes the stock record from the database. Due to foreign key constraints configured in the database schema, all associated price history records are automatically deleted as well through a cascade delete. This ensures no orphaned data remains in the database after a stock is removed.


FR7: View All Active Stock Listings
------------------------------------

The stock market page displays all approved stocks in a comprehensive table. Each row shows the ticker symbol, current price, sector, and return percentages for different time periods (24 hours, 1 month, 6 months, and 1 year). This gives users an at-a-glance view of market performance.

The sector filter allows users to narrow down the listing to specific sectors. When a user clicks the filter button, a dialog appears with checkboxes for each sector. Users can select one or multiple sectors and click apply to filter the view. The clear filter button restores the full listing.

The implementation queries the database for all stocks with their most recent prices and calculates return percentages on the fly. The results are displayed in a Tkinter Treeview widget that supports sorting and scrolling for large datasets.


FR8: Time-framed Returns Analysis
----------------------------------

The time-framed returns analysis calculates percentage changes in stock prices over different periods. For each selected stock, the system retrieves price records from 1 month ago, 6 months ago, and 1 year ago. It then compares these historical prices to the current price and calculates the percentage change.

The formula used is simple: ((current price - historical price) / historical price) * 100. This gives the return percentage for each time period. The analysis report displays these results in a table format that clearly shows which stocks have performed well and which have declined.

Users can export the report to a text file for record keeping or further analysis. The export functionality formats the data in a readable table structure that can be opened in any text editor.


FR9: Valuation Comparison
--------------------------

Valuation comparison shows the current market capitalisation of selected stocks. For each stock, the system retrieves the current price and the total number of shares outstanding. The market capitalisation is calculated by multiplying these two values together.

The report also includes the 1 year growth percentage, which shows how much the stock's value has changed over the past year. This helps investors identify which companies have grown significantly versus those that have remained stable or declined.

The comparison report makes it easy to see the relative sizes of different companies. A stock with a high share price but few shares might have a smaller total valuation than a stock with a lower price but many more shares in circulation.


FR10: Sector Benchmarking
--------------------------

Sector benchmarking compares individual stocks to their sector average. The system first groups all stocks by sector and calculates the average 1 year return for each sector. Then, for each selected stock, it compares that stock's 1 year return to its sector's average.

The difference is displayed as a plus or minus percentage. A positive difference means the stock outperformed its sector, while a negative difference means it underperformed. This analysis helps identify which stocks are sector leaders and which are lagging behind their peers.

The calculation ensures that stocks are only compared within their own sector. A technology stock is compared to other technology stocks, while a healthcare stock is compared to other healthcare stocks. This provides meaningful comparisons between similar companies.


FR11: Performance Consistency Analysis
---------------------------------------

The consistency score measures how stable a stock's returns have been over time. The system calculates this by looking at the variance between the 1 month, 6 month, and 1 year return percentages. Stocks with similar returns across all time periods have low variance and receive high consistency scores.

The formula calculates the standard deviation of the three return percentages and then converts this into a score out of 100. A score close to 100 indicates very consistent performance with minimal volatility. Lower scores indicate more volatile stocks where returns fluctuate significantly between time periods.

This analysis helps risk-averse investors identify stable stocks that are less likely to experience sudden drops in value. It complements the return percentages by adding a measure of predictability to the investment decision.


FR12: Market Report Generation
-------------------------------

The market report provides an overview of the entire stock exchange. Unlike other analyses, it does not require any stocks to be selected because it analyses the complete market.

The report calculates several key metrics. Total companies listed is simply a count of all stock records in the database. Total market valuation sums up the market capitalisation of every listed company. Average valuation divides the total by the count to give a typical company size.

The sector distribution section breaks down the market by sector. It counts how many stocks belong to each sector and calculates what percentage of the total market each sector represents. This shows which sectors dominate the exchange and which are less represented.

3. NON-FUNCTIONAL REQUIREMENTS IMPLEMENTATION
================================================================================

Non-Functional Requirements

NR1: Privacy and Data Handling
-------------------------------

Password security is handled through SHA-256 hashing which transforms passwords into a fixed-length string of characters before they are saved to the database. When a user creates an account, their password is immediately hashed using this algorithm. The actual password text is never stored in the database at any point. This means even if someone gained access to the database file, they would only see the hashed values which cannot be reversed back into the original passwords.

When a user attempts to log in, the system takes the password they entered and hashes it using the same SHA-256 algorithm. It then compares this newly generated hash against the hash that was stored during registration. If the two hashes match, the password is correct and the user is authenticated. If they do not match, login is denied.

The password input fields throughout the application are configured to mask what the user types. Instead of showing the actual characters, each keystroke displays as an asterisk symbol. This prevents someone looking over the user's shoulder from seeing their password as it is being typed. Combined with the hashing in the database, this provides robust password security at both the interface and storage levels.

Error messages in the system are deliberately generic to avoid leaking information about user accounts. When login fails, the system always displays "Invalid username or password" regardless of whether the username exists or the password was incorrect. This prevents potential attackers from testing different usernames to determine which accounts exist in the system. If the error message said "Username not found" versus "Incorrect password", an attacker could use this to build a list of valid usernames.

NR2: Data Integrity Validation
-------------------------------

The database schema enforces data integrity through CHECK constraints built into the table definitions. These constraints act as rules that every piece of data must follow before it can be saved. For the stock table, there are CHECK constraints ensuring that proposed shares and proposed valuations must always be positive numbers greater than zero. The price history table has a similar constraint ensuring that all stock prices are positive.

These database-level constraints provide a safety net that catches any invalid data even if it somehow bypasses the application's validation logic. If a bug in the code tried to insert a negative share value or a zero price, the database itself would reject the operation and return an error. This prevents corrupted data from ever being stored.

Additional validation happens at the application level before data even reaches the database. When a company fills out an application form, the validation function checks that shares are positive, that the valuation falls within the 100 million to 500 billion pound range, and that the ticker format matches the required pattern of 3 to 4 capital letters. If any validation rule fails, the function collects all the errors and displays them to the user in clear messages explaining what needs to be corrected.

This dual-layer approach where both the application and database perform validation ensures data integrity is maintained throughout the system. Even in unexpected scenarios like database manipulation attempts or future code changes, the constraints prevent invalid data from corrupting the system.

NR3: Availability and Database Connection
------------------------------------------

The system ensures high availability through automatic database initialisation that runs every time the application starts. When the program launches, it attempts to connect to the database file in the data directory. If the database does not exist or tables are missing, the initialisation function creates everything from scratch.

This means the system can recover from complete database loss without any manual intervention. If a tester accidentally deletes the database file and then restarts the application, the system will detect the missing database and automatically rebuild the entire structure including all necessary tables. It will also repopulate the sectors table with the standard sector categories like Technology, Healthcare, Finance, and others. The application becomes fully functional again without requiring database restoration from backups.

Database connections are managed carefully throughout the code to prevent connection leaks. Each function that needs database access opens a new connection, performs its operation, and then explicitly closes the connection when finished. The code uses try-finally blocks to ensure connections are closed even if an error occurs during the database operation.

This connection management prevents the application from holding unnecessary database locks. If connections were left open, they could cause availability issues where other parts of the system cannot access the database because existing connections have locked certain tables. By properly closing every connection, the system ensures database resources are always available for the next operation.

NR4: Performance
----------------

Performance optimisation starts with the database schema which includes indexes on frequently queried columns. An index on the application status column speeds up queries that filter pending, approved, or rejected applications. Another index on the price history table covering stock ID and date makes it much faster to retrieve historical prices for specific stocks on specific dates.

Without these indexes, the database would need to scan every row in the table to find matching records. With large datasets containing thousands of applications or hundreds of thousands of price records, these full table scans would become noticeably slow. The indexes create a sorted lookup structure that allows the database to jump directly to relevant rows without scanning everything.

The return percentage calculations are optimised to retrieve only the specific price records needed rather than loading all price history into memory. When calculating a one month return, the system queries for just two prices: the current price and the price from 30 days ago. It does not load the 366 days of price history and then filter through them in Python. This targeted query approach keeps response times low even as the amount of historical data grows.

For the market report feature, a single SQL query calculates all the needed statistics using aggregation functions like COUNT, SUM, and AVG. The database engine processes these aggregations very efficiently, handling thousands of records in milliseconds. This is much faster than retrieving all stock records into Python and then looping through them to calculate totals and averages manually.

NR5: Usability
--------------

The user interface prioritises clarity through descriptive labelling throughout the application. Every button clearly states what action it will perform rather than using generic labels like "Submit" or "OK". For example, the application form has a button labelled "Submit Application" and the manager portal has buttons labelled "Approve Application" and "Reject Application". This removes any ambiguity about what will happen when the user clicks.

Form field labels are positioned directly next to or above their corresponding input boxes and include helpful hints about the expected format. The proposed ticker field label reads "Proposed Ticker (3-4 capital letters):" which tells users both what information is needed and what format it should take. Users do not need to refer to separate documentation or guess what format is expected.

Error messages are designed to be specific and helpful. When validation fails, the system does not just say "Invalid input" but instead provides a precise explanation of the problem. If a ticker is too short, the message states "Ticker must be between 3 and 4 characters long". If a valuation is below the minimum, the message explains "Valuation must be at least £100 million to meet MSEG listing requirements". Some messages even include the reason for the rule, helping users understand why their input was rejected.

This attention to clear communication reduces user frustration and helps people complete their tasks successfully on the first attempt. When errors do occur, users immediately understand what went wrong and how to fix it rather than having to experiment with different inputs or contact support for clarification.

NR6: Scalability
----------------

The system is designed to scale as the number of stocks and applications grows over time. Database queries use efficient SQL operations that can handle large datasets without significant performance degradation. For the market statistics report, a single query uses aggregation functions to calculate the total number of stocks, total market valuation, and average valuation across all listings.

Using SQL aggregation functions leverages the database engine's optimised processing capabilities. The database can calculate these statistics across thousands of records much faster than if the application retrieved all records into Python and then looped through them to calculate totals. This approach scales well because the performance remains good even as the dataset grows from hundreds to thousands of stocks.

The user interface components are built to handle large amounts of data efficiently. The Treeview widgets that display stock listings and application tables include scrollbars and use a rendering approach where only the visible rows are kept in memory. When displaying 500 stocks, the widget does not try to render all 500 rows at once. Instead it renders only the 20 or 30 rows that fit on screen, and renders additional rows as the user scrolls.

This virtualisation technique means the interface remains responsive regardless of how much data exists in the database. Adding more stocks does not slow down the interface because the rendering workload stays constant based on screen size rather than growing with the dataset size. The system can comfortably handle the expected growth to hundreds of stocks without requiring architectural changes.

NR7: Reliability and Deterministic Calculations
------------------------------------------------

All financial calculations in the system use consistent formulas that produce the same results every time they are run. The return percentage calculation follows a standard formula: it takes the difference between current and historical price, divides by the historical price, and multiplies by 100 to get a percentage. This calculation is completely deterministic, meaning the same input prices will always produce the exact same output percentage.

Price history generation uses a random walk algorithm when a stock is first approved, but once those prices are generated they are stored permanently in the database and never change. The random walk creates 366 days of historical prices with daily variations of plus or minus 1.5 percent. These prices are saved to the database in a single batch operation during the approval process.

After this initial generation, any analysis that uses these prices will produce identical results every time it runs. If you calculate a stock's one month return today, close the application, and calculate the same stock's one month return again tomorrow, you will get exactly the same percentage. The underlying price data has not changed, so the calculation result remains consistent.

Sector benchmarking calculations are also completely deterministic. The system calculates the average one year return for each sector using the SQL AVG function which always produces the same result for the same input data. If five technology stocks have one year returns of 10%, 15%, 20%, 25%, and 30%, the technology sector average will always calculate to 20%. Running this calculation multiple times, on different days, or even on different computers will always produce the same result as long as the same stock returns are in the database.

This reliability in calculations is essential for a stock exchange system where users need to trust that the performance data and analysis results are accurate and consistent. Investors making decisions based on these analyses need confidence that the numbers will not change randomly between viewings.


================================================================================
4. CONCLUSION
================================================================================

The Manchester Stock Exchange system successfully implements all functional and non-functional requirements through a combination of careful database design, robust validation, and thoughtful user interface construction. The modular architecture makes the system maintainable and extensible, while the validation layers ensure data integrity is never compromised.

Performance optimisations like database indexing and efficient queries mean the system can scale to handle hundreds of stocks and thousands of price records without degradation. The security measures protect sensitive user data, particularly passwords which are never stored in plain text.

The user interface prioritises clarity and ease of use with descriptive labels, helpful error messages, and a logical workflow that guides users through each task. The consistent calculation formulas ensure that financial analyses are reliable and repeatable, which is critical for a stock exchange system where accuracy matters greatly.

Overall, the implementation demonstrates a solid understanding of both functional requirements (what the system must do) and non-functional requirements (how well the system must do it). The combination of good database practices, input validation, efficient queries, and clear UI design results in a system that is both functional and professional.
